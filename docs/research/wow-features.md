# 푸디픽 "와우 포인트" 리서치 — 사례 + 기술 타당성

- 조사일: 2026-07-13 (병렬 리서치 에이전트 2개: 사례 / 이메일 기술 한계)
- 질문: 뉴스레터 에이전트(푸디)에 "이게 된다고?" 하는 기능이 뭐가 가능한가
- 결론 선요약: **이메일 안에서의 화려한 인터랙션은 죽은 길**(AMP·CSS핵). 살아있는 와우는
  ① 원클릭 투표 ② AI 푸디 답장 ③ 클릭 이력 기반 개인 큐레이션 ④ 매직링크 개인 리캡 페이지 —
  넷 다 기존 스택(FastAPI+Resend+Postgres)과 T-003 추적 인프라를 재활용하며, **Activity Score의
  이벤트 소스를 겸한다** (= 프로젝트 핵심 가치와 복리 관계).

---

## 0. 전제: 이메일 클라이언트에서 뭐가 되고 뭐가 죽었나

| 기술 | 판정 | 근거 |
|---|---|---|
| AMP for Email | ❌ **배제 확정** | Gmail/Yahoo만 지원(Outlook 2020년 철수), 발신자 사전 심사 1~4주, **Resend API에 AMP 파라미터 자체가 없음** — 물리적으로 발송 불가 |
| CSS-only 인터랙티브 (체크박스 핵·탭) | ❌ 배제 | Gmail이 `<input>`·`:checked` 무력화, **네이버는 `<style>` 태그를 통째로 제거** — 동작하는 곳은 Apple Mail뿐 |
| 원클릭 링크 (투표·CTA) | ✅ 전 클라이언트 | 그냥 `<a>` 태그 — Gmail/네이버/Outlook/Apple 전부 동작 |
| 수신자별 개인화 HTML | ✅ 가능 | Resend Batch API 호출당 100건 개별 본문 → 3,000명 = 30회 호출 |
| 수신자별 동적 이미지 | ⚠️ 조건부 | Gmail 프록시가 URL 단위 캐싱 → 수신자별 고유 URL이면 동작, 단 재오픈은 캐시본(카운트다운·실시간 득표율 과신 금물) |
| 답장 수신(inbound) | ✅ **Resend Inbound (2025-11 출시)** | 추가 요금 없음(발송량 합산 과금), `email.received` 웹훅으로 파싱 완료 JSON 수신, 답장 스레딩 문서화 |
| mailto: 프리필 | ✅ | to/subject/body 프리필 광범위 지원 (긴 body는 잘림 주의) |
| .ics 캘린더 | ⚠️ 렌더링 비일관 | 실전 해법: "Google 캘린더에 추가"/"Outlook에 추가" 웹 링크 + .ics 다운로드 병행 |

→ **와우는 이메일 "안"이 아니라 "링크 너머(웹)·답장·다음 호"에서 일어난다.**

## 1. 사례에서 배운 것 (요지)

- **Morning Brew**: 리퍼럴 마일스톤 + 이메일 내 진행바 — 초기 성장의 80%가 리퍼럴. 비활성 구독자 재참여 캠페인으로 오픈율 125% 개선(우리 Active/Dormant 분류와 동일 발상).
- **1440 / Clean Plates / 802Ed**: 원클릭 폴(답변=링크) → "다음 호에 결과 공개"로 재오픈 루프. 폴 클릭은 전달률에도 긍정 신호.
- **뉴닉(고슴이)**: 캐릭터 화자 = 브랜드 자산 + 매호 수백 건 독자 피드백을 데이터로 활용. 푸디의 국내 벤치마크. 단 고슴이는 사람이 씀.
- **The Rundown AI**: 가입 직후 퀴즈 → 맞춤 온보딩. 오픈율 51.7%.
- **rasa.io**: 구독자별 클릭 이력으로 매호 다른 기사 5~7개 자동 선별(1:1 발송). 유의미한 개인화까지 클릭 데이터 2~4주 필요. AMA 10만 구독자 사례.
- **핵심 공백 발견**: "AI 캐릭터가 답장까지 해주는 뉴스레터"의 검증된 대형 사례는 국내외 모두 없음. 페르소나 프롬프팅 + AI 답장 에이전트(콜드메일 업계 상용화)라는 부품은 다 있는데 조합한 사람이 없다. → **선례 없는 빈 자리 = 진짜 와우 후보.**

## 2. 와우 포인트 후보 — 실행 매트릭스

| # | 아이디어 | 와우 강도 | 난이도(1 dev) | 시점 | Score 연동 |
|---|---|---|---|---|---|
| W1 | **원클릭 투표/퀴즈** — 답변=고유 링크, 다음 호에 결과 공개 | 중 | **하 (1~2일)** | 파일럿 1호부터 | poll_vote = 클릭보다 강한 신호 |

| — | 완전 1:1 발송(rasa.io식) | 상 | QA 복잡도 급증 | 배제 | W3 섹션 교체 절충안으로 충분 |

### 관통 컨셉: "푸디가 나를 기억한다"

W1~W4는 개별 기능이 아니라 하나의 서사다 — 투표하면(W1) 다음 호에 결과로 답하고,
답장하면(W2) 푸디가 대답하고, 읽은 걸(W3) 다음 호가 기억하고, 분기마다(W4) 나의 기록을 보여준다.
**전부 T-003 이벤트 테이블 하나에서 나온다.** 추적 인프라가 곧 와우 인프라.

## 3. 구현 시 주의 (설계 단계에서 결정할 것)

- **봇 클릭 방어 (W1 필수)**: 회사 Outlook Safe Links·보안 스캐너가 링크를 선제 클릭 → 허위 투표.
  대응: 봇 UA 필터 + 랜딩 페이지 확정 단계(또는 member당 최종 1표 멱등 설계 — C4 사상과 동일).
  이건 투표만이 아니라 **클릭 추적(T-003) 전체의 정확도 문제**이기도 함.
- **AI 답장 가드레일 (W2)**: 초기엔 "초안 생성 → 관리자 승인 → 발송" 모드. 답장 분류(질문/피드백/수신거부 요청)
  후 수신거부 요청은 즉시 자동 처리.
- **⚠️ 정보통신망법 (전 호 공통)**: 수신동의를 받았어도 **광고성이면 제목 앞 "(광고)" 표기 별도 필요**.
  순수 정보성은 예외지만 **디저트 코너(행사 CTA)가 들어가는 호는 광고성 판정 가능** →
  발송 파이프라인에 호별 판단(행사 포함 시 제목 처리) 로직 필요. 법무 확인 권장.
- **네이버 메일**: `<style>` 제거되므로 **모든 CSS 인라인 + 600px 테이블** — 목업을 발송용 템플릿으로
  옮길 때 인라인화 필수. 네이버 대량 발송은 화이트도메인 등록 검토(1차 출처 미확보 — 추가 확인 필요).
- 투표/추적 링크 도메인은 발송 도메인(news.foodtech-center.org)과 일치시켜 평판 분산 방지.

## 4. 출처 신뢰도 메모

사례 수치 일부는 매체 자체 발표·마케팅 블로그 출처(특히 rasa.io/AMA 42%, Rundown 매출) — 외부 검증 안 된 값.
기술 판정(Resend Inbound, Batch API 한도, Gmail 프록시, 네이버 style 제거)은 공식 문서·전문 테스팅 업체 근거.
