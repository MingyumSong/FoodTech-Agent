# T-016 중간 착지 페이지 — 진짜 체류 시간 측정

Type: FEAT
Status: WONTFIX — 착수하지 않는다 (2026-08-18 결정)

## 접은 이유 (2026-08-18)

이 티켓이 스스로 건 조건은 **"T-015 결과를 보고 착수 여부 결정"** 이었다. 그 결과가 나왔고,
결정은 **접는다** 다.

1. **T-015 근사치가 이미 의사결정에 충분하다.** 측정가능 47%·중앙값 13초·튕김 24 : 중간 23 :
   정독 16 — "절반이 제목만 보고 닫는다"는 결론을 내는 데 정밀도가 부족하지 않았다. 이 티켓이
   더해주는 건 **정밀도이지 새 결론이 아니다.**
2. **기간이 안 맞는다.** 남은 미해결 질문(이탈 비용)은 **2주 A/B** 로만 답이 나오는데
   프로젝트 종료(2026-08-29)까지 11일이다. 시작해도 답을 못 받는다.
3. **추적을 건드린다.** 기사 링크를 수신자별로 바꿔야 하고(T-013이 금지한 "원본 URL 변형"을
   의도적으로 깨는 일), 그러면 T-003 매칭이 `engagement.py`·`pilot_daily.py`·`admin_pages.py`
   3곳에서 2경로를 지원해야 한다. **종료 직전에 추적 경로를 두 갈래로 만드는 건 가장 하기 싫은
   종류의 변경이다** — 추적이 깨지면 Score·등급이 통째로 무의미해진다.
4. **기회비용.** 같은 시간을 T-023(등급 발송 진입점)에 써야 한다. 프로젝트 핵심 가치는
   "추적 → 점수 → 분류"인데 분류대로 보내는 코드가 아직 0줄이다. 지표 정밀도를 위해
   핵심 산출물의 시간을 쓰는 건 거래가 맞지 않는다.

**따라서 유지되는 전제**: 기사 링크는 계속 **원본 URL 그대로** 나간다(T-013 규칙). T-003의
clicked url 매칭은 한 경로만 지원하면 된다. 이 티켓이 깨려던 전제는 깨지지 않는다.

**이 티켓이 남긴 것**(버려지지 않음):
- T-018(`news_items.source` 복원)은 이 티켓 시안에 실데이터를 넣어보다 발견됐고 이미 DONE이다.
- A/B 배정 설계 — "조 단위 배정 금물, 점수 순위로 5블록×5명 층화 배정"은 파일럿 그룹 간
  사전 참여도가 2배 이상 차이나기 때문이고(T-019), **다른 실험을 할 때도 그대로 유효하다.**

**되살릴 조건**: 프로젝트가 연장되거나 본 발송(3,400명)이 안정된 뒤, 체류 정밀도가 실제 의사결정을
가로막는 상황이 생기면 다시 연다. 그때는 A/B 2주를 확보할 수 있는지부터 확인할 것.

## Problem

- 현재 동작: 뉴스레터의 기사 링크는 언론사 원문으로 직행한다. 우리는 "눌렀다"까지만 알고,
  그 뒤 3초를 봤는지 5분을 봤는지 알 수 없다.
- 기대 동작: 기사 링크가 우리 도메인의 요약 카드 페이지를 한 번 거치고, 그 페이지에서
  체류 시간·스크롤 깊이·"원문 보기" 클릭 여부를 정확히 기록한다.
- 왜 필요한가: T-015의 연속 클릭 간격은 근사치이고 마지막 클릭을 못 잰다. 우리 페이지를 거치면
  실측이 된다. **덤으로 파일럿 #0에서 관찰된 "지역지 원문의 모바일 렌더 불량"도 해결된다** —
  요약 카드는 우리가 렌더하므로 어떤 매체든 모바일에서 읽힌다.

## Context

관련 파일·함수:

- `app/services/newsletter_template.py` — `_main_card`/`_headline_item`이 `item["url"]`을 그대로
  href에 넣는다. 여기가 링크 생성 지점.
- `app/services/engagement.py` + `app/routes/webhooks.py` — **여기가 핵심 위험 지점.**
  T-003은 clicked 이벤트의 URL 문자열로 `news_items.url`을 매칭한다. 링크를 우리 리다이렉트로
  바꾸면 웹훅이 실어 보내는 URL이 우리 URL이 되므로 매칭 로직을 함께 고쳐야 한다.
- `app/models/news_item.py` — 착지 페이지가 보여줄 제목·요약·분야·출처.
- `app/models/engagement_event.py` — `event_type` 자유 문자열 + `payload` JSONB
  (체류 이벤트도 여기에 적재 가능할 것으로 보이나, 대용량이라 설계 시 재검토).
- `app/routes/unsubscribe.py` — 토큰 기반 공개 라우트 패턴 참고.

## 착수 전에 답해야 할 질문 — 2026-08-04 조사 결과

**Q1 이탈 비용 — 미해결. 이것만 코드로 답할 수 없다.**
클릭이 한 단계 늘면 원문 도달률이 얼마나 떨어지는지는 실측해야 한다. 다행히 **A/B 인프라가 이미 있다**:
`member_programs`에 `pilot-lab-1`~`pilot-lab-5`가 5명씩 존재하고 `_group_no_by_member`가 읽는다.
일부 그룹만 착지 링크로 보내고 나머지는 직행으로 두면 1~2주면 답이 나온다.
이 값이 크면 "지표를 얻고 읽기를 잃는" 거래이므로 티켓을 접는다.

**Q2 저작권 — 해결. 위험 낮음.**
`news.py`의 요약은 `_strip_html(entry.get("description",""))[:300]` — 매체가 RSS/API로 **스스로 배포하는
스니펫**을 300자로 자른 값이다. 본문 스크래핑은 어디에도 없다(T-013에서 재확인).
제목 + 이 스니펫 + 출처 + 원문 링크는 검색엔진·RSS 리더가 하는 것과 같은 범위다.
→ **300자 상한을 유지하고 "원문 보기"를 가장 눈에 띄게 두는 조건**으로 진행 가능. 본문 전재는 여전히 금지.

**Q3 T-003 매칭 — 해결. 오히려 더 단단해진다. 단 3곳을 고쳐야 한다.**
클릭 URL이 `{base}/r/{news_item_id}`가 되면 문자열 일치 대신 id 파싱이라 URL 정규화에 안 깨진다.
고칠 곳: `engagement.py:67`(원본 저장), `pilot_daily.py:258·277`, `admin_pages.py:263·266`
(둘 다 `{NewsItem.url: category}` 사전 조회). `dwell.py`는 url을 안 써서 영향 없음.
**과거 이벤트는 옛 URL로 남으므로 두 경로를 다 지원해야 한다** — 이게 실질 작업량의 대부분.

**Q4 체류 이벤트 볼륨 — 해결. heartbeat 대신 단발 비콘.**
heartbeat(15초)면 파일럿 25명은 하루 ~300건이라 무해하지만, 본발송 3,000명에서는
5기사 × 3,000 × 2~3 = **하루 3~4.5만 건**이 된다. 대신 페이지를 떠날 때
`navigator.sendBeacon`으로 **총 체류 + 최대 스크롤을 1건만** 보내면 조회당 1건 = 하루 1.5만 건으로
떨어지고, `engagement_events`(대용량 전제 설계)에 그대로 담을 수 있어 별도 테이블이 필요 없다.

**부수 효과(측정과 무관한 독립 이득)**: 착지 페이지는 우리가 렌더하므로 파일럿 #0에서 관찰된
**"지역지 원문의 모바일 렌더 불량"이 함께 해결**된다. T-009와 겹치는 가치다.
